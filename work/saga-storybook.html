Design system

Component library and guidelines for web and app

2026 · Product design · Front-end

One shared set of components, rules and writing guidance, used by designers, developers and AI coding tools alike.

Role
  • Design system owner: guidelines and components in code
Delivered
  • Guideline pages
  • Components and design tokens
  • Reviews of design system changes
Scope
  • Shared across product teams

The problem

Several teams build the new customer portal, more and more with AI. Without shared rules that everyone follows, screens drift apart, and problems are caught late in a design review.

How I approached it

I made the guidelines part of the same codebase as the product, owned by the design team. Then I added checks, so the rules are followed while we build.

Checks that keep the rules

I built checks that make sure the rules are followed while the product is being built. The guideline pages are read before a new screen is planned, and again when it is built.

If a screen breaks a rule, the check fails and flags it, and the change waits for our review. Questions the guidelines do not answer come to us too, and the answer is added to the page.

Designers own it, in code

The design system lives in the same codebase as the product, and the design team owns that part of it. No change to a component, a token or a guideline page goes in without our approval.

I make the changes myself. I write the page, build the component and send it for review, with AI as my partner. A colleague checks each change, but we no longer wait for a handover to keep the system up to date.
